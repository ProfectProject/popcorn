## 🤔 멱등성이란 무엇인가요?

**멱등성(Idempotency)**이란 동일한 요청을 여러 번 실행해도 **처음 실행한 결과와 동일한 결과**를 보장하는 성질입니다.

![멱등성 개념](https://static.toss.im/assets/payments/contents/payments-thumb-2.jpg)
*토스페이먼츠의 멱등성 가이드 이미지*

### 📖 멱등성의 어원과 수학적 개념

**"멱등(冪等)"**이라는 용어는 수학에서 나온 개념입니다:

- **멱(冪)**: 거듭제곱을 의미
- **등(等)**: 같다는 의미

수학에서 어떤 연산을 여러 번 적용해도 결과가 변하지 않는 성질을 말합니다.

#### 🧮 수학적 예시
```
f(x) = f(f(x)) = f(f(f(x))) = ...

예시:
- 절댓값: |5| = ||5|| = |||5||| = 5
- 최대값: max(3,5,2) = max(max(3,5,2)) = 5
- 올림함수: ceil(4.2) = ceil(ceil(4.2)) = 5
```

### 🌐 HTTP와 REST API에서의 멱등성

HTTP 메서드에는 **본래부터 멱등성을 가진 메서드들**이 있습니다:

#### ✅ 멱등한 HTTP 메서드

| HTTP 메서드 | 멱등성 | 설명 | 예시 |
|------------|--------|------|------|
| **GET** | ✅ | 조회만 하므로 몇 번 호출해도 같은 결과 | `GET /users/123` |
| **PUT** | ✅ | 전체 리소스를 교체하므로 결과 동일 | `PUT /users/123` |
| **DELETE** | ✅ | 이미 삭제된 리소스 재삭제해도 결과 동일 | `DELETE /users/123` |
| **HEAD** | ✅ | 헤더만 조회하므로 멱등함 | `HEAD /users/123` |
| **OPTIONS** | ✅ | 지원 메서드만 확인하므로 멱등함 | `OPTIONS /users` |

#### ❌ 멱등하지 않은 HTTP 메서드

| HTTP 메서드 | 멱등성 | 설명 | 문제점 |
|------------|--------|------|---------|
| **POST** | ❌ | 새 리소스 생성 시마다 새로운 결과 | 중복 클릭 시 여러 개 생성 |
| **PATCH** | ❌ | 부분 수정 시 상태에 따라 결과 달라짐 | 증감 연산 시 누적 적용 |

### 🎭 PopCorn에서의 멱등성 핵심 개념

#### 1. **부작용(Side Effect) 제거 - PopCorn 예시**
```java
❌ 부작용이 있는 주문 생성 (멱등하지 않음):
@PostMapping("/api/orders")
public OrderCreatedDto createOrder(Authentication auth, @RequestBody CreateOrderRequest request) {
    // 매번 실행시마다 새로운 주문이 생성됨!
    return orderService.createNewOrder(auth.getPrincipal().getUserId(), request);
}

요청 결과:
첫 번째 실행: 주문 생성 → orderId: "O20260115-001", amount: 24,000원
두 번째 실행: 주문 생성 → orderId: "O20260115-002", amount: 24,000원 (중복 주문!)
세 번째 실행: 주문 생성 → orderId: "O20260115-003", amount: 24,000원 (또 중복!)

💸 결과: 캐러멜팝콘 6개, 총 72,000원 결제 😱

✅ 멱등한 주문 생성:
@Idempotent(
    keyExpression = "#authentication.principal.userId + ':create_order:' + T(java.time.LocalDate).now() + ':' + #request.popupId",
    keyPrefix = "order_creation"
)
@PostMapping("/api/orders")
public OrderCreatedDto createOrder(Authentication auth, @RequestBody CreateOrderRequest request) {
    // 같은 날 같은 팝업에 대해서는 한 번만 주문 생성
    return orderService.createIdempotentOrder(auth.getPrincipal().getUserId(), request);
}

요청 결과:
첫 번째 실행: 주문 생성 → orderId: "O20260115-001", amount: 24,000원
두 번째 실행: 캐시 응답 → orderId: "O20260115-001", amount: 24,000원 (동일 주문!)
세 번째 실행: 캐시 응답 → orderId: "O20260115-001", amount: 24,000원 (동일 주문!)

🎉 결과: 캐러멜팝콘 2개, 총 24,000원만 결제 ✅
```

## 🚨 왜 멱등성이 중요한가요?

### 1. 사용자 실수 방지
- 버튼 중복 클릭
- 새로고침으로 인한 재요청
- 네트워크 지연으로 인한 재시도

### 2. 시스템 안정성 향상
- 네트워크 오류로 인한 재시도 요청
- 마이크로서비스 간 통신에서의 중복 호출
- 메시지 큐에서의 중복 메시지 처리

### 3. 데이터 무결성 보장
- 중복 결제 방지
- 중복 주문 방지
- 중복 데이터 생성 방지

### 실제 사례: 중복 결제의 무서움

```
💸 중복 결제 사고 사례

고객: 25,000원 팝콘 주문
네트워크 오류로 재시도
결과: 50,000원 중복 결제 😱

❌ 문제점:
• 고객 클레임 폭증
• 환불 처리 비용
• 브랜드 신뢰도 하락
• 금융 감독 이슈
```

## 🏗️ PopCorn에서의 멱등성 구현

### 🔄 멱등성이 동작하는 과정 (쉽게 이해하기)

```
1️⃣ 사용자가 "주문하기" 버튼을 누름
   │
   ▼
2️⃣ IdempotentAspect (검사 로봇)가 낚아챔
   "어? 이 메서드에 @Idempotent 스티커가 붙어있네?"
   │
   ▼
3️⃣ 키 만들기
   "user123 + create_order + 2026-01-15 + popup456"
   → "user123:create_order:2026-01-15:popup456"
   │
   ▼
4️⃣ 캐시(기억저장소)에서 찾아보기
   RedisBasedIdempotencyService: "이 키 본 적 있나?"
   │
   ├─ 🆕 없음 → "처음 보는 요청이네! 실행하자!"
   │   │
   │   ├─ 실제 주문 생성 로직 실행
   │   ├─ 결과를 키와 함께 Redis에 저장
   │   └─ 고객에게 "주문 완료!" 응답
   │
   └─ ✅ 있음 → "아! 이미 처리한 요청이네!"
       │
       ├─ Redis에서 저장된 결과 가져오기
       └─ 고객에게 "이미 주문 완료됨!" 응답
```

### 아키텍처 개요

```
📱 사용자 요청
    ↓
🎯 @Idempotent 어노테이션
    ↓
🔄 IdempotentAspect (AOP)
    ↓
💾 RedisBasedIdempotencyService
    ↓
🔴 Redis 분산 캐시 + 동시성 제어
```

### 핵심 구성 요소

#### 1. `@Idempotent` 어노테이션
```java
@Idempotent(
    keyExpression = "#request.orderId",
    keyPrefix = "order_creation",
    ttlSeconds = 1800,
    responseType = OrderCreatedDto.class
)
public OrderCreatedDto createOrder(CreateOrderRequest request) {
    // 주문 생성 로직
}
```

#### 2. `IdempotentAspect` (AOP)
- SpEL 표현식을 사용한 동적 키 생성
- 메서드 실행 전/후 멱등성 처리
- 예외 상황 처리

#### 3. `RedisBasedIdempotencyService`
- Redis를 사용한 분산 캐싱
- 여러 서버 간 멱등성 공유
- 동시 요청 감지 및 처리
- JSON 직렬화/역직렬화를 통한 응답 저장

### 📁 Redis 기반 구현 예시

#### Redis 기반 멱등성 서비스 구현
```java
// 파일: RedisBasedIdempotencyService.java
@Service
@ConditionalOnProperty(name = "popcorn.idempotency.enabled", havingValue = "true")
public class RedisBasedIdempotencyService implements IdempotencyService {

    private final RedisTemplate<String, Object> redisTemplate;
    private final ObjectMapper objectMapper;
    private final RedisLockManager lockManager;

    public RedisBasedIdempotencyService(
            RedisTemplate<String, Object> redisTemplate,
            ObjectMapper objectMapper,
            RedisLockManager lockManager) {
        this.redisTemplate = redisTemplate;
        this.objectMapper = objectMapper;
        this.lockManager = lockManager;
    }

    @Override
    public <T> IdempotencyResult<T> processRequest(
            String idempotencyKey,
            IdempotentOperation<T> operation,
            Class<T> responseType,
            int ttlSeconds) throws Exception {

        String cacheKey = generateCacheKey(idempotencyKey);
        String lockKey = generateLockKey(idempotencyKey);

        // 1. Redis에서 기존 결과 확인
        String cachedResult = (String) redisTemplate.opsForValue().get(cacheKey);
        if (cachedResult != null) {
            log.debug("Redis 캐시 히트: key={}", cacheKey);
            T result = objectMapper.readValue(cachedResult, responseType);
            return IdempotencyResult.cachedExecution(result, getCachedExecutionTime(cacheKey));
        }

        // 2. 분산 락 획득 시도 (동시 요청 방지)
        boolean lockAcquired = lockManager.tryLock(lockKey, Duration.ofSeconds(30));
        if (!lockAcquired) {
            throw new IdempotencyException("동시에 처리 중인 요청이 있습니다: " + idempotencyKey);
        }

        try {
            // 3. 락 획득 후 다시 한번 Redis 확인 (Double-checked locking)
            cachedResult = (String) redisTemplate.opsForValue().get(cacheKey);
            if (cachedResult != null) {
                T result = objectMapper.readValue(cachedResult, responseType);
                return IdempotencyResult.cachedExecution(result, getCachedExecutionTime(cacheKey));
            }

            // 4. 실제 로직 실행
            log.debug("Redis 캐시 미스 - 새 요청 실행: key={}", cacheKey);
            T result = operation.execute();
            LocalDateTime executionTime = LocalDateTime.now();

            // 5. 결과를 Redis에 저장
            String resultJson = objectMapper.writeValueAsString(result);
            redisTemplate.opsForValue().set(cacheKey, resultJson, Duration.ofSeconds(ttlSeconds));

            // 실행 시간도 별도로 저장
            redisTemplate.opsForValue().set(
                cacheKey + ":execution_time",
                executionTime.toString(),
                Duration.ofSeconds(ttlSeconds)
            );

            log.debug("Redis에 결과 저장 완료: key={}, ttl={}초", cacheKey, ttlSeconds);
            return IdempotencyResult.newExecution(result);

        } finally {
            lockManager.unlock(lockKey);
        }
    }

    private String generateCacheKey(String idempotencyKey) {
        return "popcorn:idempotent:cache:" + idempotencyKey;
    }

    private String generateLockKey(String idempotencyKey) {
        return "popcorn:idempotent:lock:" + idempotencyKey;
    }

    private LocalDateTime getCachedExecutionTime(String cacheKey) {
        String timeStr = (String) redisTemplate.opsForValue().get(cacheKey + ":execution_time");
        return timeStr != null ? LocalDateTime.parse(timeStr) : LocalDateTime.now();
    }

    @Override
    public IdempotencyCacheStats getCacheStats() {
        // Redis 정보를 통해 통계 생성
        RedisInfo info = redisTemplate.execute((RedisCallback<RedisInfo>) connection -> {
            Properties properties = connection.info("memory");
            return new RedisInfo(properties);
        });

        return new RedisIdempotencyCacheStats(
            info.getUsedMemory(),
            info.getMaxMemory(),
            countIdempotencyKeys(),
            0.0 // Redis는 별도 히트율 측정 로직 필요
        );
    }

    private long countIdempotencyKeys() {
        Set<String> keys = redisTemplate.keys("popcorn:idempotent:cache:*");
        return keys != null ? keys.size() : 0;
    }
}
```

```java
public class RedisLockManager {

    private final RedisTemplate<String, Object> redisTemplate;

    public RedisLockManager(RedisTemplate<String, Object> redisTemplate) {

    public boolean tryLock(String lockKey, Duration timeout) {

        Boolean acquired = redisTemplate.opsForValue()

            "end";

        );
```

```java
        List<Exception> exceptions = new CopyOnWriteArrayList<>();
        List<String> results = new CopyOnWriteArrayList<>();

                throw new RuntimeException(e);
```

### 1. 키 설계의 기본 원칙

멱등성 키는 **비즈니스 로직의 고유성을 정확히 반영**해야 합니다. 너무 넓으면 불필요한 차단이, 너무 좁으면 중복 실행이 발생할 수 있습니다.

#### ✅ PopCorn에서 사용하는 좋은 키 설계 예시

```java
// 1. 시간 범위가 명확한 키 설계
@Idempotent(
    // 사용자별 + 날짜별 + 팝업별로 고유성 보장
    keyExpression = "#authentication.principal.userId + ':create_order:' + T(java.time.LocalDate).now() + ':' + #request.popupId",
    keyPrefix = "order_creation",
    ttlSeconds = 86400 // 하루 동안만 캐시 유지
)
public OrderCreatedDto createOrder(Authentication auth, CreateOrderRequest request) {
    // 같은 날, 같은 사용자, 같은 팝업에 대해서는 중복 주문 방지
    // 다음 날이 되면 새로 주문 가능
    return orderCommandService.createOrder(auth, request);
}

// 2. 결제처럼 절대 중복되면 안 되는 작업
@Idempotent(
    // 주문ID + 결제키 조합으로 완전한 고유성 보장
    keyExpression = "#request.orderId + ':toss_confirm:' + #request.paymentKey",
    keyPrefix = "payment_confirm",
    ttlSeconds = 3600 // 1시간 동안 캐시
)
public TossPaymentConfirmResponse confirmPayment(TossPaymentConfirmRequest request) {
    // 같은 주문에 대해 같은 결제키로는 절대 중복 승인 불가
    return tossPaymentService.confirmPayment(request);
}

// 3. 상태 변경처럼 의미가 명확한 키
@Idempotent(
    // 특정 결제의 특정 상태로의 변경만 중복 방지
    keyExpression = "#paymentId + ':status_change:' + #request.status",
    keyPrefix = "payment_status"
)
public PaymentDetailResponse changePaymentStatus(String paymentId, PaymentStatusChangeRequest request) {
    // PENDING -> COMPLETED는 중복 방지하지만
    // COMPLETED -> CANCELLED은 별개 작업으로 처리
    return paymentService.changeStatus(paymentId, request);
}
```

#### ❌ 피해야 할 나쁜 키 설계

```java
// 너무 포괄적인 키 - 사용자의 모든 작업이 차단됨
@Idempotent(keyExpression = "#authentication.principal.userId")
public OrderDto doSomething(Authentication auth) {
    // 이 사용자는 하나의 작업이 끝날 때까지 아무것도 할 수 없음!
}

// 의미가 불분명한 키 - 무엇을 방지하는지 알 수 없음
@Idempotent(keyExpression = "#id + ':process'")
public ResultDto process(String id) {
    // 어떤 프로세스인지 명확하지 않음
}

// 시간 범위가 없는 키 - 영원히 캐시됨
@Idempotent(keyExpression = "#userId + ':daily_report'")
public ReportDto generateDailyReport(Long userId) {
    // 한번 생성하면 영원히 같은 보고서만 반환
}
```

### 2. TTL(Time To Live) 설정 전략

TTL은 **비즈니스 요구사항과 시스템 성능을 고려**하여 설정해야 합니다.

#### 📊 PopCorn 프로젝트 TTL 가이드

| 작업 유형 | 권장 TTL | 실제 코드 예시 | 설정 이유 |
|-----------|----------|----------------|-----------|
| **결제 승인** | 1시간 (3600초) | `ttlSeconds = 3600` | 결제 실패 시 빠른 재시도 허용, 하지만 중복 승인은 절대 방지 |
| **일일 주문** | 24시간 (86400초) | `ttlSeconds = 86400` | 하루 동안은 중복 주문 방지, 다음 날은 새 주문 허용 |
| **보고서 생성** | 30분 (1800초) | `ttlSeconds = 1800` | 리소스 집약적 작업의 과도한 실행 방지 |
| **API 호출** | 5분 (300초) | `ttlSeconds = 300` | 외부 API 부하 방지, 짧은 시간 내 중복 호출 차단 |

#### 💡 TTL 설정 실제 예시

```java
// 결제 승인 - 1시간 TTL
@Idempotent(
    keyExpression = "#orderId + ':payment_confirm'",
    ttlSeconds = 3600, // 1시간
    keyPrefix = "payment_confirm"
)
public PaymentConfirmResponse confirmPayment(String orderId) {
    // 결제 실패 시 1시간 내에는 재시도 가능하지만
    // 성공 시에는 1시간 동안 중복 승인 완전 차단
    return paymentGateway.confirm(orderId);
}

// 하루 한 번만 가능한 작업 - 24시간 TTL
@Idempotent(
    keyExpression = "#userId + ':daily_action:' + T(java.time.LocalDate).now()",
    ttlSeconds = 86400, // 24시간
    keyPrefix = "daily_action"
)
public ActionResult performDailyAction(Long userId) {
    // 하루에 한 번만 실행 가능한 액션
    // 자정이 지나면 다시 실행 가능 (날짜가 바뀌므로)
    return actionService.performDaily(userId);
}

// 리소스 집약적 작업 - 30분 TTL
@Idempotent(
    keyExpression = "#reportType + ':generate:' + T(java.time.LocalDateTime).now().truncatedTo(T(java.time.temporal.ChronoUnit).HOURS)",
    ttlSeconds = 1800, // 30분
    keyPrefix = "report_generation"
)
public ReportDto generateReport(String reportType) {
    // 시간 단위로 키를 생성하여 30분 동안 캐시
    // 같은 시간대에는 같은 보고서 재사용
    return reportService.generate(reportType);
}
```

### 3. 응답 타입 명시 가이드

Jackson 직렬화/역직렬화가 정확히 동작하도록 **복잡한 타입은 반드시 명시**해야 합니다.

#### ✅ 응답 타입을 명시해야 하는 경우

```java
// 1. Generic 타입이 포함된 응답
@Idempotent(
    keyExpression = "#orderId",
    responseType = ApiResponse.class // Generic 타입 명시 필요
)
public ApiResponse<OrderDetailDto> getOrderDetail(String orderId) {
    return ApiResponse.success(orderService.getDetail(orderId));
}

// 2. 복잡한 중첩 객체 구조
@Idempotent(
    keyExpression = "#reportId",
    responseType = ComplexReportResponse.class // 복잡한 객체 구조 명시
)
public ComplexReportResponse generateComplexReport(UUID reportId) {
    return reportService.generateComplex(reportId);
}

// 3. 상속 관계가 있는 응답 타입
@Idempotent(
    keyExpression = "#paymentId",
    responseType = TossPaymentResponse.class // 구체적인 타입 명시
)
public TossPaymentResponse getPaymentDetail(String paymentId) {
    return (TossPaymentResponse) paymentService.getDetail(paymentId);
}
```

### 4. 실무에서 자주 사용하는 SpEL 표현식 패턴

#### 🔧 시간 관련 표현식

```java
// 현재 날짜 (yyyy-MM-dd 형태)
T(java.time.LocalDate).now()

// 현재 시각을 시간 단위로 절삭 (yyyy-MM-ddTHH)
T(java.time.LocalDateTime).now().truncatedTo(T(java.time.temporal.ChronoUnit).HOURS)

// 현재 시각을 분 단위로 절삭 (yyyy-MM-ddTHH:mm)
T(java.time.LocalDateTime).now().truncatedTo(T(java.time.temporal.ChronoUnit).MINUTES)

// 현재 연월 (yyyy-MM 형태)
T(java.time.YearMonth).now()
```

#### 🔧 문자열 조작 표현식

```java
// null 체크와 기본값 설정
#request.orderId ?: 'default'

// 문자열 길이 체크
#request.description != null && #request.description.length() > 0 ? #request.description : 'empty'

// 문자열 일부만 사용 (처음 10글자)
#request.longText.substring(0, T(Math).min(10, #request.longText.length()))
```

#### 🔧 컬렉션 처리 표현식

```java
// 리스트 크기
#request.items.size()

// 리스트의 첫 번째 요소
#request.items[0].productId

// 리스트를 문자열로 결합
#request.productIds.![#this].toString()
```

## ❓ 자주 묻는 질문

### Q1. 멱등성 키를 어떻게 설계해야 하나요?

**A:** 비즈니스 로직에 맞는 고유한 키를 설계하세요.

```java
// 사용자별 일일 액션
"user:{userId}:action:{action}:date:{date}"

// 주문별 결제
"order:{orderId}:payment:{method}"

// 특정 리소스에 대한 작업
"resource:{resourceId}:operation:{operation}:user:{userId}"
```

### Q2. 캐시가 만료되면 중복 실행이 가능한가요?

**A:** 네, TTL이 지나면 새로 실행됩니다. 이는 의도된 동작입니다.

```java
// 30분 후에는 다시 실행 가능
@Idempotent(keyExpression = "#orderId", ttlSeconds = 1800)
```

### Q3. 실패한 요청도 캐시되나요?

**A:** 기본적으로 실패한 요청은 캐시되지 않습니다. `retryOnFailure = false`로 설정하면 실패도 캐시됩니다.

```java
// 실패 시에도 재시도 차단
@Idempotent(
    keyExpression = "#orderId",
    retryOnFailure = false
)
```

### Q4. 동시 요청이 들어오면 어떻게 되나요?

**A:** 첫 번째 요청만 실행되고, 나머지는 `IdempotencyException`이 발생합니다.

```java
// 동시 요청 처리
catch (IdempotencyException e) {
    // 동시 요청임을 클라이언트에 알림
    return ResponseEntity.status(HttpStatus.CONFLICT)
        .body("동시 처리 중인 요청이 있습니다.");
}
```

### Q5. 어떤 메서드에 멱등성을 적용해야 하나요?

**A:** 다음과 같은 경우에 적용하세요:

- **✅ 적용해야 하는 경우:**
  - 결제/주문 처리
  - 데이터 생성/수정
  - 외부 API 호출
  - 리소스 집약적인 작업

- **❌ 적용하지 말아야 하는 경우:**
  - 단순 조회 (이미 GET 요청은 멱등)
  - 로그 기록
  - 실시간 데이터 (현재 시간 등)

### Q6. 메모리 사용량이 걱정됩니다.

**A:** Redis는 TTL 기반으로 메모리를 자동 관리합니다:

```java
// PopCorn의 Redis TTL 설정
redisTemplate.opsForValue().set(
    cacheKey,
    resultJson,
    Duration.ofSeconds(ttlSeconds)  // TTL 후 자동 삭제
);

// Redis 메모리 정책 (application.yml)
spring:
  redis:
    timeout: 2000ms
    # Redis 자체적으로 LRU 정책으로 메모리 관리
```

## 🔧 문제 해결 가이드

### 문제 1: SpEL 표현식 오류

**증상:** `SpEL 표현식 평가 실패` 로그 메시지

**원인:** 잘못된 표현식이나 존재하지 않는 속성 접근

**해결방법:**
```java
// ❌ 잘못된 예시
@Idempotent(keyExpression = "#request.nonExistentField")

// ✅ 올바른 예시
@Idempotent(keyExpression = "#request.orderId")
// 또는 null 체크 포함
@Idempotent(keyExpression = "#request.orderId ?: 'default'")
```

### 문제 2: 직렬화 오류

**증상:** `응답 직렬화 실패` 오류

**원인:** Jackson이 직렬화할 수 없는 객체

**해결방법:**
```java
// DTO 클래스에 기본 생성자와 getter 추가
public class OrderResponseDto {
    private String orderId;
    private String status;

    // 기본 생성자 필요
    public OrderResponseDto() {}

    // getter 메서드들 필요
    public String getOrderId() { return orderId; }
    public String getStatus() { return status; }
}
```

### 문제 3: 동시 요청 오류가 너무 자주 발생

**증상:** `IdempotencyException: 동시에 처리 중인 요청이 있습니다`

**원인:** 요청 처리가 너무 오래 걸리거나 실제 동시 요청

**해결방법:**
```java
// 1. 요청 처리 성능 개선
// 2. 클라이언트에서 중복 클릭 방지
// 3. 동시 요청 처리 로직 추가
@ExceptionHandler(IdempotencyException.class)
public ResponseEntity<String> handleIdempotency(IdempotencyException e) {
    return ResponseEntity.status(HttpStatus.CONFLICT)
        .body("잠시 후 다시 시도해주세요.");
}
```

### 문제 4: 캐시 효율이 떨어짐

**증상:** 캐시 히트율이 낮음

**원인:** 키 설계가 부적절하거나 TTL이 너무 짧음

**해결방법:**
```java
// 1. 키 설계 검토 - 너무 구체적이지 않게
// ❌ 밀리초까지 포함한 키
"user:123:action:2025-01-15T10:30:45.123"

// ✅ 적절한 범위의 키
"user:123:action:2025-01-15"

// 2. TTL 늘리기
@Idempotent(
    keyExpression = "#userId",
    ttlSeconds = 3600  // 1시간으로 증가
)
```
